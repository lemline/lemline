How to cancel, resume, or suspend a workflow

This guide explains what you can do today to stop, pause or recover a running workflow instance in Lemline.

Current Status

Lemline does not yet provide operator commands to act on a running instance. There is no CLI command, gRPC gateway call or dashboard action to cancel, suspend, resume or retry an instance.

Operation

Available as an operator action

What to do instead

Cancel

No

Design the workflow to stop on a cancellation event or a timeout

Suspend / Resume

No

Design the workflow to wait for an event before continuing

Retry a faulted instance

No

Use retry on the failing task, or start a new instance

The rest of this guide shows how to build these behaviors into the workflow itself.

Prepare the examples

Complete the SQLite setup and keep its worker running. Run the commands from a second terminal in the setup directory. With the JAR, substitute java -jar lemline.jar for bin/lemline. The examples need no shop. They react to events that this publisher sends on the worker's SQLite event channel. Save it as tutorial-publisher.yaml and register it (skip it if you registered it in the tutorial):

document: dsl: '1.0.3' namespace: examples name: tutorial-publisher version: '1.0.0' do: - publish: emit: event: with: type: ${ .type } source: https://events.example.com/tutorial data: ${ .data }
bin/lemline definition post -f tutorial-publisher.yaml

Start each listening instance first, then publish its event. An event only resumes the instances already waiting for it.

Stopping a Workflow on Request

Let the workflow listen for a cancellation event while it waits, and end when it arrives:

document: dsl: '1.0.3' namespace: examples name: stopping-a-workflow-on-request version: '1.0.0' do: - waitForPaymentOrCancellation: listen: to: any: - with: type: com.example.payment.received - with: type: com.example.order.cancelled read: envelope - checkCancellation: switch: - cancelled: when: ${ .[0].type == "com.example.order.cancelled" } then: markCancelled - default: then: continue - markPaid: set: status: paid then: exit - markCancelled: set: status: cancelled

Save it as stopping-a-workflow-on-request.yaml. Start one instance and cancel it, then start another and pay it:

bin/lemline definition post -f stopping-a-workflow-on-request.yaml bin/lemline instance start examples stopping-a-workflow-on-request bin/lemline instance start examples tutorial-publisher --input '{"type":"com.example.order.cancelled","data":{"orderId":"ORD-401"}}' bin/lemline instance start examples stopping-a-workflow-on-request bin/lemline instance start examples tutorial-publisher --input '{"type":"com.example.payment.received","data":{"orderId":"ORD-402"}}'

The first instance completes with {"status":"cancelled"}, the second with {"status":"paid"}. Each instance resumes a few seconds after its event. This example matches events by type only, so start the second instance after the first has completed. Add a correlate rule to match an order ID, as in How to emit and listen for events.

Send the cancellation as a CloudEvent on the CloudEvents channel of the workflow's namespace. See How to emit and listen for events.

Bounding How Long a Workflow Waits

Lemline does not enforce workflow-level timeouts yet, nor timeouts on tasks other than listen: they are accepted but ignored. To keep an instance from waiting forever for an external signal, put a timeout on the listen task:

document: dsl: '1.0.3' namespace: examples name: bounding-how-long-a-workflow-waits version: '1.0.0' do: - waitForPayment: try: - listenForPayment: listen: to: one: with: type: com.example.payment.received timeout: after: seconds: 30 catch: errors: with: type: https://open-workflow-specification.org/spec/1.0.0/errors/timeout do: - markExpired: set: status: expired

When the timeout expires, the task faults with a timeout error (status 408), which the try task catches here. The example waits 30 seconds so that you can see both outcomes; a real payment wait would use hours. See Timeouts.

Save it as bounding-how-long-a-workflow-waits.yaml. Pay the first instance in time, and let the second expire:

bin/lemline definition post -f bounding-how-long-a-workflow-waits.yaml bin/lemline instance start examples bounding-how-long-a-workflow-waits bin/lemline instance start examples tutorial-publisher --input '{"type":"com.example.payment.received","data":{"orderId":"ORD-403"}}' bin/lemline instance start examples bounding-how-long-a-workflow-waits

The first instance completes with the payment data, [{"orderId":"ORD-403"}]. The second completes with {"status":"expired"} 30 to 40 seconds later: the worker checks expired waits every 10 seconds.

Pausing Until an External Signal

A listen task pauses the instance until a matching event arrives; a wait task pauses it for a fixed duration. Neither uses runner resources while waiting.

document: dsl: '1.0.3' namespace: examples name: pausing-until-an-external-signal version: '1.0.0' do: - waitForApproval: listen: to: one: with: type: com.example.order.approved - recordApproval: set: approvedBy: ${ .[0].approver }

Save it as pausing-until-an-external-signal.yaml, start it, then send the approval:

bin/lemline definition post -f pausing-until-an-external-signal.yaml bin/lemline instance start examples pausing-until-an-external-signal bin/lemline instance start examples tutorial-publisher --input '{"type":"com.example.order.approved","data":{"orderId":"ORD-404","approver":"manager"}}'

The instance stays paused until the approval arrives, then completes with {"approvedBy":"manager"}.

Recovering from Failures

  • Inside the workflow: wrap fragile tasks in try with a retry policy, so temporary errors are retried automatically. See Implementing Retry Mechanisms.

  • After a fault: a faulted instance stays faulted. Fix the cause, then start a new instance with lemline instance start.

  • Instances of a namespace no worker serves: instance start succeeds, but the instance does not run. On the SQLite setup, its message waits in the queue: add the namespace to lemline.namespaces and restart the worker, and the instance runs. With a shared broker, a worker that receives a message for a namespace it does not serve parks it in the failures table; re-send it with bin/lemline failures replay once a worker serves that namespace. On SQLite, failures replay --dry-run answers No failures found with reason 'foreign_namespace'.
