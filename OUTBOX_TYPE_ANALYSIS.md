# Outbox and State Storage Analysis

## Type Hierarchy

```
WorkflowState (sealed)
├── WorkflowCommand (sealed) - Used for resuming workflow execution
│   ├── ResumeFromTask
│   └── ResumeFromStartedTask
└── WorkflowEvent (sealed) - Generated by WorkflowOrchestrator
    ├── WorkflowCompleted
    ├── TaskFailed
    ├── TaskScheduled
    ├── WaitStarted
    ├── RetryScheduled
    ├── RunWorkflowStarted
    ├── ForkStarted
    └── ForkBranchCompleted
```

## Critical Insight: Type Transformation Requirement

**EVENTS** are what the Processor/Orchestrator **produces**
**COMMANDS** are what the MessageHandler **consumes**

Each relevant WorkflowEvent has a `.resume()` method that creates the corresponding WorkflowCommand:
- `RetryScheduled.resume()` → `WorkflowCommand.ResumeFromTask` (no parameters)
- `WaitStarted.resume()` → `WorkflowCommand.ResumeFromStartedTask` (no parameters)
- `TaskScheduled.resume()` → `WorkflowCommand.ResumeFromTask` (no parameters)
- `RunWorkflowStarted.resumeSync(output)` → `WorkflowCommand.ResumeFromStartedTask` (**requires output parameter**)
- `RunWorkflowStarted.resumeAsync()` → `WorkflowCommand.ResumeFromStartedTask` (no parameters)
- `ForkStarted.resume(rawOutput)` → `WorkflowCommand.ResumeFromStartedTask` (**requires output parameter**)

## Two Distinct Patterns

### Pattern A: Scheduled Outbox (Time-Based Processing)
- Data written to database
- **Scheduled relay** periodically queries for due entries
- Relay transforms Event → Command and sends to workflow channel
- Resume transformation requires **no external input**

### Pattern B: Event-Driven State Storage (Waiting for External Events)
- Data written to database to preserve workflow state
- **Event-driven handler** processes when external event occurs (child completion, branch completion)
- Handler transforms Event → Command using external data and sends immediately
- Resume transformation requires **external input** (child output, branch output)

## 1. lemline_retries Table ✅ PATTERN A: Scheduled Outbox

### Classification
- **Pattern**: Scheduled Outbox (Time-Based Processing)
- **Model**: `RetryOutboxModel`
- **WorkflowState Type Stored**: `InstanceMessage<WorkflowEvent.RetryScheduled>`
- **Transformation**: `event.resume()` → `WorkflowCommand.ResumeFromTask` (no parameters needed)

### Who Writes / When
- **Writer**: `DatabaseMessageHandler.handleWorkflowPersistence()`
- **Trigger**: InstanceMessageHandler receives `RetryScheduled` event from WorkflowOrchestrator
- **When**: After retry delay is calculated by TryInstance in workflow execution
- **Location**: DatabaseMessageHandler.kt:161-169

```kotlin
is WorkflowEvent.RetryScheduled -> {
    retryRepository.insert(
        RetryOutboxModel.from(
            instance = instance as InstanceMessage<WorkflowEvent.RetryScheduled>,
            outboxScheduledFor = state.retryAt,  // Future timestamp
            error = IllegalStateException(...),
            reason = "Task retry"
        )
    )
}
```

### Who Reads / When
- **Reader**: `RetryOutbox` (scheduled relay)
- **Schedule**: Every N seconds (configured via `lemline.outbox.retry.outbox.every`)
- **Query**: `SELECT * FROM lemline_retries WHERE status='PENDING' AND delayed_until <= NOW() FOR UPDATE SKIP LOCKED`
- **Location**: OutboxRelay.kt via OutboxRepository.findEntitiesToProcess()

### Who Processes / When
- **Processor**: `RetryOutbox.process()`
- **Trigger**: Scheduled relay finds due entries
- **Action**: Transform Event → Command, send to workflow channel
- **Location**: RetryOutbox.kt (extends AbstractOutbox)

### Current Issue
```kotlin
// AbstractOutbox.kt:77-79 - WRONG
open suspend fun process(entity: T) {
    instanceEmitter.send(entity.instanceMessage)  // ⚠️ SENDS EVENT!
}
```
**PROBLEM**: Sends `InstanceMessage<WorkflowEvent.RetryScheduled>` but emitter expects `InstanceMessage<out WorkflowCommand>`

### Required Fix
```kotlin
// RetryOutbox.kt - CORRECT
override suspend fun process(entity: RetryOutboxModel) {
    val command = entity.instanceMessage.workflowState.resume()
    instanceEmitter.send(
        InstanceMessage(
            workflowInfo = entity.instanceMessage.workflowInfo,
            workflowState = command,
            parentId = entity.instanceMessage.parentId
        )
    )
}
```

## 3. lemline_parents Table ❌ PATTERN B: Event-Driven State Storage

### Classification
- **Pattern**: Event-Driven State Storage (Waiting for Child Completion)
- **Model**: `ParentOutboxModel` (MISNOMER - not really outbox!)
- **WorkflowState Type Stored**: `InstanceMessage<WorkflowEvent.RunWorkflowStarted>`
- **Transformation**: `event.resumeSync(output)` → `WorkflowCommand.ResumeFromStartedTask` (**requires child output parameter**)

### Who Writes / When
- **Writer**: `DatabaseMessageHandler.handleRunWorkflowStarted()`
- **Trigger**: InstanceMessageHandler receives `RunWorkflowStarted` event from WorkflowOrchestrator
- **When**: RunWorkflow task executed with `sync: true` (parent waits for child)
- **Location**: DatabaseMessageHandler.kt:195-224

```kotlin
private suspend fun handleRunWorkflowStarted(instance: InstanceMessage<WorkflowEvent.RunWorkflowStarted>) {
    parentRepository.withTransaction { conn ->
        // Store parent state (paused, waiting for child)
        parentRepository.insert(
            ParentOutboxModel(
                id = parentId,
                instanceMessage = instance,  // Stores RunWorkflowStarted event
                outboxScheduledFor = null    // Not time-based!
            ),
            connection = conn
        )

        // Create and send child workflow message
        instanceEmitter.send(childMessage)
    }
}
```

### Who Reads / When
- **Reader**: `DatabaseMessageHandler.handleWorkflowCompleted()`
- **Trigger**: Child workflow completes, sends `WorkflowCompleted` event with `parentId`
- **When**: Immediately upon child completion (event-driven, NOT scheduled)
- **Query**: `SELECT * FROM lemline_parents WHERE id = ? FOR UPDATE`
- **Location**: DatabaseMessageHandler.kt:229-259

### Who Processes / When
- **Processor**: `DatabaseMessageHandler.handleWorkflowCompleted()` (**NOT ParentOutbox!**)
- **Trigger**: Child completion event received
- **Action**: Transform Event → Command using child output, send immediately
- **Location**: DatabaseMessageHandler.kt:233-246

```kotlin
instance.parentId?.let { parentId ->
    parentRepository.withTransaction { conn ->
        parentRepository.findById(parentId, conn)?.let { parent ->
            val state = parent.instanceMessage.workflowState

            // Transform Event → Command WITH child output
            instanceEmitter.send(
                InstanceMessage(
                    workflowInfo = parent.instanceMessage.workflowInfo,
                    workflowState = state.resumeSync(instance.workflowState.output), // ← Needs output!
                    parentId = parent.parentId,
                )
            )

            // Mark as processed
            parent.outBoxStatus = OutBoxStatus.SENT
            parentRepository.update(parent, conn)
        }
    }
}
```

### Why NOT a True Outbox?
- **No scheduled relay**: `ParentOutbox.outboxConf = null`
- **ParentOutbox.process() is DEAD CODE**: Never called
- **Event-driven**: Triggered by child completion, not time
- **Requires external data**: Child output needed for transformation
- **Immediate processing**: Not batched, not retried by relay

### Design Issue
- `ParentOutboxModel` extends `OutboxModel` but doesn't follow outbox pattern
- Should be renamed to `ParentStateModel` or `ParentWaitingModel`
- Should NOT extend `OutboxRepository` - different access pattern

## 4. lemline_schedules Table ✅ PATTERN A: Scheduled Outbox (Special Case)

### Classification
- **Pattern**: Scheduled Outbox (Time-Based Processing)
- **Model**: `ScheduleOutboxModel`
- **WorkflowState Type Stored**: `InstanceMessage<WorkflowCommand>` ✅ (NOT Event!)
- **Transformation**: None needed - already stores Commands for **starting new workflows**

### Who Writes / When
- **Writer**: User/API via `DefinitionMessageHandler` or `ScheduleOutbox` itself (self-updating)
- **Trigger**: User creates scheduled workflow definition
- **When**: Schedule created or updated for next execution
- **Location**: ScheduleOutboxModel.from:122-164

```kotlin
ScheduleOutboxModel(

    instanceMessage = InstanceMessage.new(  // Creates NEW workflow instance
        workflowId = workflowId,
        workflowNamespace = workflowNamespace,
        workflowName = workflowName,
        workflowVersion = workflowVersion,
        workflowInput = workflowInput,
        parentId = null,
    ),  // Returns InstanceMessage<WorkflowCommand.ResumeFromTask> (start command)
    scheduleEvery = scheduleEvery,
    scheduleAfter = scheduleAfter,
    scheduleCron = scheduleCron,
    scheduleZone = zoneId?.id,
    outboxScheduledFor = scheduledFor  // Next execution time
)
```

### Who Reads / When
- **Reader**: `ScheduleOutbox` (scheduled relay)
- **Schedule**: Every N seconds (configured via `lemline.outbox.schedule.outbox.every`)
- **Query**: `SELECT * FROM lemline_schedules WHERE status='PENDING' AND delayed_until <= NOW() FOR UPDATE SKIP LOCKED`
- **Location**: OutboxRelay.kt via OutboxRepository.findEntitiesToProcess()

### Who Processes / When
- **Processor**: `ScheduleOutbox.process()`
- **Trigger**: Scheduled relay finds due entries
- **Action**: Send Command to start new workflow instance, update for next execution
- **Location**: ScheduleOutbox.kt:58-64

```kotlin
override suspend fun process(entity: ScheduleOutboxModel) {
    // Calculate next scheduled time and update entity
    entity.prepareNextScheduled(WorkflowId.random())

    // Send the workflow start command
    super.process(entity)  // Sends WorkflowCommand ✅
}
```

### Why This Works
- **Intentional design**: Schedules START new workflows, not RESUME existing ones
- **No Event transformation needed**: Creates fresh `WorkflowCommand.start()` directly
- **Self-updating**: Calculates next execution time after processing
- **Different semantics**: Not resuming paused state, but starting new instance with same definition

## 5. lemline_forks Table ❌ PATTERN B: Event-Driven State Storage

### Classification
- **Pattern**: Event-Driven State Storage (Waiting for Branch Completions)
- **Model**: `ForkModel` (NOT outbox!)
- **WorkflowState Type Stored**: `InstanceMessage<WorkflowEvent.ForkStarted>`
- **Transformation**: `event.resume(rawOutput)` → `WorkflowCommand.ResumeFromStartedTask` (**requires aggregated branch outputs**)
- **Additional Storage**: `lemline_fork_branches` table tracks individual branch completions

### Who Writes / When
- **Writer**: `DatabaseMessageHandler.handleForkStarted()`
- **Trigger**: InstanceMessageHandler receives `ForkStarted` event from WorkflowOrchestrator
- **When**: Fork task executed (parallel branch execution)
- **Location**: DatabaseMessageHandler.kt:279-341

```kotlin
private suspend fun handleForkStarted(instance: InstanceMessage<WorkflowEvent.ForkStarted>) {
    val state = instance.workflowState

    // Create fork metadata
    val forkModel = ForkModel(
        instanceMessage = instance,  // Stores ForkStarted event
        forkPosition = state.nodePosition.toString(),
        compete = isCompete,
        branchCount = branches.size
    )

    // Create branch tracking rows
    val branchModels = branches.mapIndexed { index, branch ->
        ForkBranchModel(
            forkId = forkModel.id,
            branchIndex = index,
            branchName = branch.name,
            status = BranchStatus.PENDING,
            ...
        )
    }

    // Atomic insert
    forkRepository.insertForkWithBranches(forkModel, branchModels)

    // Send branch execution messages
    branches.forEach { branch ->
        instanceEmitter.send(branchMessage)
    }
}
```

### Who Reads / When
- **Reader**: `ForkRepository.recordBranchCompletion()`
- **Trigger**: Branch workflow completes, sends `ForkBranchCompleted` event
- **When**: Immediately upon each branch completion (event-driven)
- **Query**:
  - `UPDATE lemline_fork_branches SET status='COMPLETED', output=?`
  - `SELECT * FROM lemline_forks WHERE id=? FOR UPDATE` (pessimistic lock)
  - `SELECT COUNT(*) FROM lemline_fork_branches WHERE fork_id=? AND status='COMPLETED'`
- **Location**: ForkRepository.kt:140-192

### Who Processes / When
- **Processor**: `ForkRepository.recordBranchCompletion()` called by `DatabaseMessageHandler.handleForkBranchCompleted()`
- **Trigger**: Each branch completion (tracks progress)
- **When Complete**: All branches done (or first in compete mode)
- **Action**: Aggregate branch outputs, transform Event → Command, send to workflow channel
- **Location**: DatabaseMessageHandler.kt:344-346 (currently incomplete/commented)


### Why NOT a True Outbox?
- **No scheduled relay**: No ForkOutbox exists
- **Event-driven**: Triggered by branch completions, not time
- **Requires external data**: Branch outputs needed for transformation

## 6. lemline_failures Table ⚠️ Terminal Storage (No Processing)

### Classification
- **Pattern**: Terminal Storage (Audit/Manual Intervention)
- **Model**: `FailureModel`
- **WorkflowState Type Stored**: `InstanceMessage<WorkflowEvent.TaskFailed>?` (nullable)
- **Transformation**: None - terminal state, never resumed

### Who Writes / When
- **Writer**: `DatabaseMessageHandler` or outbox relay error handlers
- **Trigger**:
  1. Workflow execution fails (TaskFailed event)
  2. Message deserialization fails
  3. Outbox processing exceeds max retry attempts
- **When**: Terminal failure conditions
- **Location**: Multiple locations

```kotlin
// 1. Workflow execution failure (DatabaseMessageHandler.kt:172-181)
is WorkflowEvent.TaskFailed -> {
    failureRepository.insert(
        FailureModel.from(
            instance = instance as InstanceMessage<WorkflowEvent.TaskFailed>,
            error = exception,
            reason = getFailureReason(exception)
        )
    )
}

// 2. Deserialization failure (DatabaseMessageHandler.kt:384-393)
failureRepository.insert(
    FailureModel.from(
        id = IDV7.random(),
        payload = message.payload,  // Raw string, can't deserialize
        error = RuntimeException(...),
        reason = DESERIALIZATION_FAILURE
    )
)

// 3. Outbox max retries exceeded (OutboxRelay.kt)
failureRepository.insert(
    FailureModel.from(
        instance = outboxEntity.instanceMessage,
        error = lastException,
        reason = OUTBOX_MAX_RETRIES_EXCEEDED
    )
)
```

### Who Reads / When
- **Reader**: Manual inspection, monitoring, debugging tools
- **Trigger**: Human intervention or monitoring alerts
- **When**: Never automatically - requires manual action
- **Query**: Ad-hoc queries for failed workflows

### Who Processes / When
- **Automatic Processor**: None - no scheduled relay
- **Manual Processing**: Will provide methods to:
  1. Retry failed workflow (re-send as-is)
  2. Resume with explicit output (transform Event → Command with user-provided output)
- **Action**: Manual investigation, then explicit retry/resume command

### Why NOT Automatic Processing?
- **Non-recoverable errors**: Logic errors, invalid workflow definitions, missing resources
- **Audit trail**: Preserves failure information for debugging
- **Manual intervention required**: User must decide how to proceed (fix definition, provide different input, etc.)
- **Both forms**: Can store `instanceMessage` (structured) OR `payload` (raw string when deserialization fails)
- **Future API**: Methods like `FailureRepository.retry(id)` or `FailureRepository.resumeWith(id, output)`

### Pattern Classification

#### Pattern A: Scheduled Outbox (Time-Based)
**Tables**: lemline_retries, lemline_waits, lemline_schedules

**Characteristics**:
- ✅ Scheduled relay polls database periodically
- ✅ Time-based triggering (delayed_until <= NOW())
- ✅ Batch processing with FOR UPDATE SKIP LOCKED
- ✅ Automatic retry on relay failures
- ✅ Extends OutboxRepository
- ✅ Transformation needs no external input
- ✅ Follows true outbox pattern

**Processing Flow**:
```
Event stored → Scheduled relay → Transform to Command → Send to workflow channel
```

#### Pattern B: Event-Driven State Storage
**Tables**: lemline_parents, lemline_forks

**Characteristics**:
- ❌ NO scheduled relay (event-driven instead)
- ❌ Triggered by external events (child completion, branch completion)
- ❌ Point queries by ID, not batch processing
- ❌ Immediate processing, not batched
- ❌ Should NOT extend OutboxRepository
- ❌ Transformation requires external data (outputs)
- ❌ NOT a true outbox pattern

**Processing Flow**:
```
Event stored → Wait for external event → Retrieve by ID → Transform with external data → Send immediately
```

#### Pattern C: Terminal Storage
**Tables**: lemline_failures

**Characteristics**:
- ⚠️ Never automatically processed
- ⚠️ Audit trail for failed workflows
- ⚠️ Manual intervention required
- ⚠️ No transformation needed

## Key Questions for Design Discussion

### Question 1: Should we type the storage?

**Pros of Type-Safe Storage (current approach)**:
- Compile-time safety - can't store wrong event type in wrong table
- Self-documenting - model clearly states what it contains
- Type-safe deserialization

**Cons of Type-Safe Storage**:
- Complexity in repository base classes (WithInstanceRepository)
- Requires unsafe casts or complex generic machinery
- Mismatch between storage type (Event) and emission type (Command)

### Question 2: Where should Event→Command transformation happen?

**Option A: In Outbox.process()** (Recommended)
```kotlin
override suspend fun process(entity: RetryOutboxModel) {
    val command = entity.instanceMessage.workflowState.resume()
    instanceEmitter.send(
        entity.instanceMessage.copy(workflowState = command)
    )
}
```
- Clear responsibility
- Works with type-safe storage
- Each outbox owns its transformation logic

**Option B: Store Commands instead of Events**
```kotlin
// Transform BEFORE saving to database
val command = event.resume()
retryRepository.insert(
    RetryOutboxModel(
        instanceMessage = instance.copy(workflowState = command)
    )
)
```
- Simpler outbox processing
- But loses information - can't see original event that triggered retry
- Harder to debug/audit

**Option C: Generic storage (no type safety)**
```kotlin
// Go back to InstanceMessage<WorkflowEvent>? for all
protected fun ResultSet.getInstanceMessage(): InstanceMessage<WorkflowEvent>?
```
- Simpler infrastructure
- Loses type safety
- More runtime errors possible

## Proposed Refactoring: Separate Hierarchies

### Current Problems
1. `ParentOutboxModel` extends `OutboxModel` but doesn't follow outbox pattern
2. `ParentOutbox` has dead code (`process()` never called)
3. Confusing naming - "Outbox" implies scheduled relay pattern
4. `AbstractOutbox` doesn't handle Event → Command transformation

### New Design: Simplified Hierarchies

#### Hierarchy 1: OutboxModel (Scheduled Pattern Only)
```kotlin
/**
 * Base for entities processed by scheduled outbox relays.
 * Time-based triggering, batch processing, automatic retries.
 *
 * ONLY for Pattern A: Scheduled Outbox
 */
@Serializable
sealed class OutboxModel : InstanceModel, WithDefiniteWorkflowInfo {
    abstract val instanceMessage: InstanceMessage<out WorkflowState>  // Events or Commands
    abstract var outBoxStatus: OutBoxStatus
    abstract var outboxScheduledFor: Instant?
    abstract var outboxDelayedUntil: Instant?
    abstract var outboxAttemptCount: Int
    abstract var outboxErrorClass: String?
    abstract var outboxErrorMessage: String?
    abstract var outboxErrorStackTrace: String?
}

// Implementations:
@Serializable data class RetryOutboxModel(
    override val instanceMessage: InstanceMessage<WorkflowEvent.RetryScheduled>
    // ... other fields
) : OutboxModel()

@Serializable data class WaitOutboxModel(
    override val instanceMessage: InstanceMessage<WorkflowEvent.WaitStarted>
    // ... other fields
) : OutboxModel()

@Serializable data class ScheduleOutboxModel(
    override val instanceMessage: InstanceMessage<WorkflowCommand>  // Special case!
    // ... other fields
) : OutboxModel()
```

### Outbox Relay Refactoring

#### Pattern A: Scheduled Outbox with Transformation
```kotlin
internal abstract class ScheduledOutbox<T : OutboxModel> : AbstractOutbox<T>() {

    /**
     * Transform stored Event to Command before sending.
     * Each subclass implements the specific transformation.
     */
    protected abstract fun transformToCommand(entity: T): InstanceMessage<out WorkflowCommand>

    final override suspend fun process(entity: T) {
        val commandMessage = transformToCommand(entity)
        instanceEmitter.send(commandMessage)
    }
}

// Implementations:
class RetryOutbox : ScheduledOutbox<RetryOutboxModel>() {
    override fun transformToCommand(entity: RetryOutboxModel) =
        InstanceMessage(
            workflowInfo = entity.instanceMessage.workflowInfo,
            workflowState = entity.instanceMessage.workflowState.resume(),  // No params
            parentId = entity.instanceMessage.parentId
        )
}

class WaitOutbox : ScheduledOutbox<WaitOutboxModel>() {
    override fun transformToCommand(entity: WaitOutboxModel) =
        InstanceMessage(
            workflowInfo = entity.instanceMessage.workflowInfo,
            workflowState = entity.instanceMessage.workflowState.resume(),  // No params
            parentId = entity.instanceMessage.parentId
        )
}

class ScheduleOutbox : ScheduledOutbox<ScheduleOutboxModel>() {
    override fun transformToCommand(entity: ScheduleOutboxModel): InstanceMessage<out WorkflowCommand> {
        entity.prepareNextScheduled(WorkflowId.random())
        return entity.instanceMessage  // Already a Command!
    }
}
```

### Migration Impact

#### Renamed Tables (for clarity)
- `lemline_parents` → `lemline_parent_waiting` (or keep as-is, just rename model)
- `lemline_forks` → `lemline_fork_waiting` (or keep as-is, just rename model)

#### Deleted Classes
- `ParentOutbox` (dead code, processing in DatabaseMessageHandler)
- `ForkOutbox` (never existed, but would be dead code)

#### Benefits
1. **Clear separation**: Scheduled outbox vs event-driven state storage vs terminal storage
2. **No dead code**: ParentOutbox.process() removed
3. **Type safety**: Each model clearly states its purpose
4. **Better naming**: "Waiting" instead of misleading "Outbox"
5. **Transformation explicit**: `transformToCommand()` method in each outbox
6. **No forced abstraction**: ParentWaitingModel and ForkWaitingModel are standalone - different enough that forcing a common base class would be over-engineering

This preserves the semantic difference: **Events = Past Facts, Commands = Future Actions**
