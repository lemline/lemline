# Jackson JSON runtime

Workflow inputs, outputs, contexts, task states, activity configurations, event collections, and the expression evaluator use Jackson `JsonNode` trees. Object and array values use `ObjectNode` and `ArrayNode` directly. The SDK, jackson-jq, and networknt validator consume those same trees; expression evaluation no longer serializes JSON to text and parses it into a second tree representation.

`LemlineJson` keeps the SDK's Jackson mixins and bean validation for workflow definitions. `JacksonNodes.kt` provides Kotlin construction and read helpers over native Jackson nodes. Runtime JSON parsing remains strict; the workflow/CLI mapper keeps its existing permissive parsing options.

## Ownership

Treat runtime trees as read-only values. Builders and scope merges create fresh containers. Custom activity executors must copy a tree before modifying it. JQ receives copies of both input and scope values so updates cannot mutate a cached definition, prior task state, or another branch's input. Multi-result JQ expressions collect emitted arrays without appending into them.

Binary SDK/CloudEvent values retain their JSON Base64 string representation. Non-finite Protobuf doubles remain decodable as numbers; non-finite JQ outputs retain their previous JSON string representation.

Integral values are normalized to `IntNode` when they fit, otherwise `LongNode`, so the concrete Java numeric type does not change equality after a durable resume. Runtime parsing uses `BigDecimal` for fractional values so decimal precision is preserved before expression evaluation and transport. Numbers crossing `google.protobuf.Value` retain the existing IEEE-754 double behavior and precision limitations.

Persisted correlation keys retain their previous double-based numeric encoding and JSON escaping. Correlation expressions use the legacy numeric view at that compatibility boundary so existing collections and listeners remain joinable without a migration. Workflow data otherwise keeps its precise native representation.

Decimal expansion is bounded to 10,000 digits at runtime/schema parsing boundaries and before validation, including referenced schemas. This prevents compact extreme exponents from causing unbounded allocation inside the validator.

Kotlin serialization remains available for typed DTOs such as lifecycle payloads and mock configuration. Its `JsonNodeSerializer` adapter works at that codec boundary without intermediate JSON text. Structured persisted correlation keys also retain their historical Kotlin JSON escaping at their codec boundary. Root and task expression scopes are built directly in Jackson and do not use this DTO adapter.

## Protobuf compatibility

No `.proto` file, field number, field type, transport codec, or database schema changes. `ProtoJsonValueMapper` maps Jackson nodes to the same maps, lists, strings, booleans, doubles, and null values accepted by Wire.

`LegacyJsonContractTest` loads bytes generated by the previous runtime at commit `bba9a3f6` and checks both the decoded command and byte-for-byte re-encoding. Existing canonical ProtoJSON fixtures and all state/command/event round-trip tests remain applicable. No worker draining or stored-definition migration is introduced by this JSON representation change.

## Benchmark

Run `scripts/benchmark-json-runtime.sh /tmp/lemline-json-benchmark`. It creates an isolated checkout of `bba9a3f6`, copies the benchmark harness with only its tree API names adapted, and runs the same workloads before and after. The temporary checkout is removed on exit. Full logs and per-sample JSON results are written into the specified directory.

The harness starts three fresh JVMs with a fixed 512 MiB heap. Each case warms up for three 300 ms windows and measures five 500 ms windows per JVM. Parsing input and workflow definitions is outside the timed region; JQ compilation stays inside it in both versions. Logging is disabled. Results are consumed through a volatile sink. Allocation uses the current thread's `ThreadMXBean` counter; these workloads execute synchronously inside `runBlocking` and do not include background-thread allocations.

The four cases cover a scalar JQ expression on 100 records, an object containing three expressions, eight sequential set tasks, and the same workflow with a binary Protobuf round trip at each resume. They measure local CPU and allocation costs, not broker/database/network throughput. This is a focused benchmark rather than a JMH suite; timing is sensitive to JVM warmup and host load.

See [measured results and raw samples](benchmarks/jackson-runtime-results.md).
