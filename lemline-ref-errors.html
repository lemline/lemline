Error Reference

This reference documents the standard error types and error handling capabilities in Lemline.

Error Structure

All errors in Lemline follow the RFC 7807 Problem Details format:

{ "type": "https://open-workflow-specification.org/spec/1.0.0/errors/validation", "status": 400, "instance": "/do/0/validateInput", "title": "Input Validation Failed", "detail": "The 'amount' field must be a positive number" }

A failed HTTP call can therefore be caught by type and by status, for example catch.errors.with: { type: https://open-workflow-specification.org/spec/1.0.0/errors/communication, status: 503 }. The Unable to reach title names the server only, never the path or the query of the URL.

Errors raised by call: a2a use the base URI https://serverlessworkflow.io/spec/1.0.0/errors/ instead: catch https://serverlessworkflow.io/spec/1.0.0/errors/communication for the failures above, and https://serverlessworkflow.io/spec/1.0.0/errors/runtime for the others, such as an error returned by the agent in its JSON-RPC answer.

Lemline only raises timeout errors for listen tasks: workflow-level timeouts and timeouts on other tasks are not enforced yet.

Gateway API Errors

The gateway exposes gRPC (and Connect) APIs. Failed calls return standard gRPC status codes, for example INVALID_ARGUMENT for an invalid request, NOT_FOUND for an unknown definition or instance, ALREADY_EXISTS, UNAUTHENTICATED, PERMISSION_DENIED and INTERNAL.

Java Exception Hierarchy

For developers working on Lemline, workflow errors are carried by a single exception type:

java.lang.RuntimeException └── com.lemline.core.errors.WorkflowException (sealed) └── com.lemline.core.errors.InternalException

An activity reports a failed exchange with an external service by throwing com.lemline.core.errors.CommunicationException, which carries the status to report; it becomes a communication error. Any other exception thrown by an activity becomes a runtime error with status 500.

InternalException holds an InternalException.Error with the standard error fields (type, status, instance, title, detail). The error type is one of the values of com.lemline.core.errors.WorkflowErrorType (configuration, validation, expression, authentication, authorization, timeout, communication, runtime).

Defining Custom Errors

Custom error types can be defined in workflow definitions:

document: dsl: '1.0.3' namespace: examples name: typed-error version: '1.0.0' use: errors: invalidOrder: type: https://errors.example.com/invalid-order status: 422 title: Invalid order do: - validateOrder: if: ${ (.orderId // "") == "" } raise: error: invalidOrder - acceptOrder: set: status: accepted

Error Handling Examples

Basic Try-Catch

document: dsl: 1.0.3 namespace: examples name: basic-try-catch version: 1.0.0 do: - secureOperation: try: - riskyTask: listen: to: one: with: type: com.example.payment.received timeout: after: seconds: 5 catch: errors: with: type: https://open-workflow-specification.org/spec/1.0.0/errors/timeout as: timeoutError do: - handleTimeout: set: processed: false reason: ${ $timeoutError.title }

Matching Multiple Error Types

A try task has a single catch. To handle several errors differently, catch them and route on the fields of the caught error in catch.do:

document: dsl: '1.0.3' namespace: examples name: matching-multiple-error-types version: '1.0.0' do: - callService: try: - request: call: http with: method: get endpoint: http://127.0.0.1:8787/products query: fail: ${ .failStatus | tostring } catch: as: error do: - routeByStatus: switch: - rateLimited: when: ${ $error.status == 429 } then: handleRateLimit - unavailable: when: ${ $error.status == 503 } then: handleUnavailable - default: then: handleOtherError - handleRateLimit: set: outcome: rate-limited then: exit - handleUnavailable: set: outcome: unavailable then: exit - handleOtherError: set: outcome: failed errorType: ${ $error.type }

Using Retry Policies

document: dsl: 1.0.3 namespace: examples name: using-retry-policies version: 1.0.0 do: - readStock: try: - operation: call: http with: method: get endpoint: http://127.0.0.1:8787/stock query: fail: '503' failTimes: '1' key: ${ $workflow.id } catch: retry: delay: seconds: 1 backoff: exponential: {} limit: attempt: count: 3 when: ${ $error.status >= 500 }

Error Debugging

When debugging errors:

  • Read the workflow.faulted and task.faulted lifecycle events of the instance in the dashboard; they carry the error type, status, title, instance (position in the workflow) and detail.

  • Run the runner with --debug to log the input of each task. Every log line carries the workflow namespace, name, version and instance id, so you can filter on the instance.

Error Handling Best Practices

  1. Be specific with error types: Catch specific error types rather than all errors

  2. Provide fallbacks: Use default values or alternative paths for common errors

  3. Use conditional retries: Only retry errors that have a chance of succeeding on retry

  4. Include context in errors: Use descriptive error messages with relevant details

  5. Log error details: Log sufficient context for debugging

  6. Use appropriate error status codes: Match HTTP status codes to semantics

  7. Define custom error types: Create domain-specific error types for your application

  8. Organize errors hierarchically: Use consistent type URIs that reflect hierarchy

docker compose -f examples/tutorial-services/compose.yaml up -d

Keep the setup worker running and use a second terminal in the setup directory.

bin/lemline definition post -f typed-error.yaml bin/lemline instance start examples typed-error bin/lemline definition post -f basic-try-catch.yaml bin/lemline instance start examples basic-try-catch bin/lemline definition post -f matching-multiple-error-types.yaml bin/lemline instance start examples matching-multiple-error-types --input '{"failStatus":429}' bin/lemline instance start examples matching-multiple-error-types --input '{"failStatus":503}' bin/lemline instance start examples matching-multiple-error-types --input '{"failStatus":404}' bin/lemline definition post -f using-retry-policies.yaml bin/lemline instance start examples using-retry-policies
